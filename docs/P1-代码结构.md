# MindButler P1 代码结构说明

> 目的：复盘时先看包边界，再看类职责。避免“接口、DTO、组件全堆在 Service 包里”。

## 1. 包职责

| 包 | 放什么 | 不放什么 |
|---|---|---|
| `Controller` | HTTP 入口、参数校验、登录态读取 | 业务规则、SQL、JSON payload 解析 |
| `Service` | **只放业务接口** | 实现类、DTO、结果对象、Spring 组件 |
| `Service.impl` | Service 接口实现、事务边界、领域编排 | 请求/响应对象、跨领域的工具逻辑 |
| `Service.support` | 有 Spring 依赖但不适合暴露为业务接口的协作组件（限流、候选净化） | Controller 直接依赖 |
| `Dto` | 请求/响应、候选、结果对象（`IntentOutcome`、`IntentExtractionResult`） | 业务逻辑、数据库访问 |
| `Entity` | 数据库行映射 | 对外 JSON 结构 |
| `Mapper` | MySQL 数据访问 | Redis、业务校验 |
| `Repository` | Redis/缓存门面 | MySQL SQL |
| `utils` | 无状态工具/解析/格式化（`IntentJsonParser`、`IntentPayloadCodec`、`IntentReplyFormatter`） | 事务、Repository/Mapper 调用 |
| `Config` | 配置绑定、启动校验、路由、拦截器、线程池 | 业务流程 |

## 2. 意图链路类图（文字版）

```text
ChatServiceimpl
  └─ IntentService (接口)
       └─ IntentServiceimpl（只做编排）
            ├─ IntentDetector            粗筛
            ├─ IntentDailyLimiter        日限流
            ├─ IntentExtractor (接口)
            │    └─ IntentExtractorimpl    LLM + timeout
            │         ├─ IntentPrompts
            │         └─ IntentJsonParser -> IntentExtractionResult
            ├─ IntentCandidateSanitizer  候选校验/截断/敏感词
            ├─ IntentPayloadCodec        pending payload 编解码
            ├─ IntentReplyFormatter      确认/结果文案
            └─ PendingActionService       pending 状态机 + 事务
```

## 3. 关键边界

- `IntentOutcome` 是**服务返回结果**，放在 `Dto`，不放 `Service`。
  - 不可变：字段 `final`，只能通过 `chat()/extracted()/confirmed()/rejected()/replyOnly()` 构造。
  - 调用方用 `shouldContinueChat()/isExtracted()/isConfirmed()/isRejected()` 判断，不能直接改字段。
- `IntentExtractionResult` 是**提取器/解析器与 Service 的边界对象**，放在 `Dto`。
  - `IntentExtractor` 不再依赖 `utils.IntentJsonParser.Parsed`。
- `IntentJsonParser` 只负责“JSON -> DTO”，不写库、不限流、不生成中文文案。
- `IntentPayloadCodec` 是 pending payload 的唯一编解码入口；IntentService 和 PendingActionService 不再各写一套 ObjectMapper。
- `IntentReplyFormatter` 只做文案，不依赖 Spring、不查库。
- `MindButlerStartupValidator` 负责启动日志/模型白名单检查；`IntentExtractorimpl` 只负责提取。
- `IntentDailyLimiter` / `IntentCandidateSanitizer` 放 `Service.support`，表示“Service 的协作组件”，不是业务接口。

## 4. 本轮结构修正

1. `IntentOutcome`：`Service` → `Dto`，public 可变字段 → private final + getter/工厂。
2. `IntentJsonParser.Parsed`：嵌套类 → 独立 `Dto.IntentExtractionResult`。
3. `IntentServiceimpl`：405 行 → 157 行；候选净化、payload、文案分别拆出。
4. `IntentDailyLimiter`：`Service` → `Service.support`。
5. 启动校验：`IntentExtractorimpl` 内的 `@PostConstruct` → `Config.MindButlerStartupValidator`。
6. `PendingActionServiceimpl`：删除自己的 ObjectMapper/payload 解析，复用 `IntentPayloadCodec`。

## 5. 仍保留的项目既有约定

以下不是 P1 新问题，属于全项目机械式重构，建议单独提交，避免和业务修复混在一起：

- `*Serviceimpl` 命名沿用现有项目（不是 `*ServiceImpl`）。
- Service 实现仍以 `@Autowired` 字段注入为主；Sonar `S6813` 会提示，但和现有代码风格一致。
- `ChatController` 等旧类仍使用 `Assert` 做部分参数校验，未统一改为 `@Valid`。

## 6. 复盘建议顺序

1. `Dto/IntentOutcome` + `Dto/IntentExtractionResult`
2. `Service/IntentService` + `IntentExtractor`（只看接口）
3. `Service/impl/IntentServiceimpl`（编排）
4. `Service/support/*`（限流、候选净化）
5. `utils/IntentJsonParser`、`IntentPayloadCodec`、`IntentReplyFormatter`
6. `Config/MindButlerStartupValidator`
7. 最后看 `PendingActionServiceimpl` 的事务与状态机
