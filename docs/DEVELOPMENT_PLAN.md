# AI Chat 项目后续开发计划（暑期求职版）

> 适用对象：想用这个项目准备暑期实习/校招后端面试，但不想把项目做成“AI 生成代码堆砌”的同学。
>
> 时间假设：每周 10~12 小时，共 10 周；时间紧可压缩到 4~6 周，时间充裕可拉长到 16 周。

## 1. 项目定位

不要把它包装成“又一个 CRUD 聊天室”。你的差异化是：

> **一个带 AI 能力、有缓存/持久化设计、能测试、能部署的 Spring Boot 后端。**

面试官真正会问的是：

- Redis 和 MySQL 为什么同时用？数据丢了怎么办？
- 流式输出怎么实现？客户端断开怎么办？
- 多用户怎么隔离？Token 怎么校验？
- 长对话上下文怎么控制？
- 你怎么测试？怎么部署？出问题怎么排查？

所以后续开发要围绕 **可靠性、工程化、AI 应用深度**，而不是堆功能。

## 2. 当前基线（2026-10-22）

已经具备：

- 手机验证码登录、密码登录、BCrypt、Token 拦截器、新用户引导
- 同步对话、SSE 流式对话、多轮上下文
- Redis 会话缓存、MySQL 用户表
- 聊天消息/会话元数据 MySQL 持久化，Redis 缓存未命中回源
- 全局异常处理、参数校验、CORS、单元测试、GitHub Actions

还需要补：

- 历史消息分页、长上下文裁剪
- 聊天/登录接口限流、更多安全加固
- 集成测试（Testcontainers）、API 测试
- RAG 知识库（可选但很加分）
- 可观测性、Docker Compose 部署
- 简历表达、架构图、面试问答

## 3. 最终目标与验收标准

完成计划后，你应该能做到：

1. 用 2 分钟讲清项目架构、核心链路和技术选型。
2. 打开任意核心文件，能解释每一行为什么这么写。
3. 能现场画图：登录、聊天、持久化、RAG、部署。
4. 有可运行的测试、CI、Docker Compose 和 README。
5. 简历上的每个数字都能给出处，不写虚假指标。
6. 至少完成一个 AI 应用亮点（RAG 或流式对话优化）。

## 4. 低 AI 依赖工作法（重要）

不是“完全不用 AI”，而是**把 AI 放在 review 和排错位置，不放在第一作者位置**。

### 4.1 硬规则

1. **先设计，后写码**：每个任务先写 5 行设计（输入、输出、存储、失败、测试）。
2. **第一版自己写**：不允许直接粘贴超过 20 行 AI 生成的代码。
3. **先跑测试再问 AI**：贴报错、日志、已尝试方案，而不是“帮我写”。
4. **20 分钟规则**：卡住先自己查官方文档/源码/日志 20 分钟；再问 AI 要“提示”，不要完整代码。
5. **每写一个类，口头解释一遍**：说不清就是没懂，回去重写。
6. **每周至少一次无 AI 编码日**：只允许查文档和 IDE。
7. **提交前自检**：命名、异常、事务、空值、日志、测试、文档。

### 4.2 推荐流程

```text
读需求 -> 画时序图 -> 写伪代码 -> 自己实现 -> 写测试
      -> 跑通 -> 让 AI 做 code review（只提问题）
      -> 自己改 -> 记录到学习日志
```

### 4.3 学习日志模板

每周在自己的笔记里记录：

```text
日期：
问题：
我的假设：
验证方式（日志/SQL/测试）：
结论：
如果重做，我会怎么设计：
```

这份日志就是面试时“你遇到过什么困难”的素材库。

## 5. 十周开发路线

### 第 1 周：吃透现有代码，固化持久化

**目标**：能独立讲清聊天持久化，不再“看不懂自己项目”。

任务：
- 画登录、同步聊天、SSE 聊天、持久化四条时序图。
- 逐行读 `ChatSessionRepositoryimpl`、`ChatPersistenceService`、两个 Mapper。
- 用 `EXPLAIN` 分析 `selectBySession`、`selectByUser` 的索引命中。
- 手工验证：删 Redis key 后，历史/会话列表/标题从 MySQL 恢复。
- 给持久化补一个失败场景测试（例如 Redis 抛异常时仍能读 MySQL）。

验收：
- 不看代码，能画出“写 MySQL → 写 Redis”和“读 Redis → 回源 MySQL”的流程图。
- 能解释为什么先写 MySQL、为什么不用 `@Async`。

面试题：
- Redis 7 天过期后数据怎么恢复？
- 为什么消息表按 id 排序而不是只按时间？

### 第 2 周：测试与工程质量

**目标**：把“能跑”变成“可验证”。

任务：
- 引入 Testcontainers（MySQL + Redis），写 `@SpringBootTest` 集成测试。
- 用 MockMvc 测登录、参数校验、未登录 401、会话隔离。
- 配置 JaCoCo，核心 Service/Repository 覆盖率目标 60%+。
- 更新 GitHub Actions：单测 + 集成测试 + 打包。
- 统一异常返回格式的测试。

验收：
- `./mvnw verify` 本地通过，CI 通过。
- 能解释单元测试和集成测试的边界。

面试题：
- 为什么要用 Testcontainers，不用 H2？
- 如何测试 Redis 缓存未命中？

### 第 3 周：安全加固

**目标**：让项目经得起“安全”追问。

任务：
- 登录验证码、聊天接口加 Redis 限流（滑动窗口或令牌桶）。
- 评估 Token 方案：当前 Redis opaque token vs JWT，写一页对比。
- 统一参数校验（Bean Validation 或现有 Assert），补边界测试。
- 检查 CORS、敏感配置、日志是否泄露密码/Token。
- 文件上传（如果做 RAG）加类型/大小限制。

验收：
- 连续请求触发 429；验证码不能重放；未登录不能访问聊天。
- 能说清 JWT 和 Redis Token 的取舍。

面试题：
- 为什么不用 JWT？/ 为什么用 JWT？
- 验证码怎么防刷、防重放？

### 第 4 周：聊天能力完善

**目标**：从“能聊”到“像个产品”。

任务：
- 历史消息分页：`beforeId` + `limit`，避免一次返回全部。
- 上下文裁剪：只取最近 N 条或按 token 估算截断；写清策略。
- 增加“重新生成”“停止生成”（如果前端配合）。
- 处理 SSE 客户端断开：保存已生成部分，避免上下文丢失。
- 消息长度、会话数量、标题长度边界测试。

验收：
- 100 轮对话不会把 Prompt 撑爆。
- 分页 API 有测试和文档。

面试题：
- 长对话怎么控制上下文？
- SSE 和 WebSocket 怎么选？
- 客户端断开后后端怎么处理？

### 第 5~6 周：RAG 知识库（最加分的 AI 亮点）

**目标**：做一个能讲清楚的 RAG MVP，不追求大而全。

任务：
- 支持上传 Markdown/TXT（有余力再加 PDF）。
- 文档解析 → 按标题/长度切分（chunk + overlap）。
- 用 Ollama embedding 模型生成向量。
- 向量存储二选一：
  - 简单版：Spring AI `SimpleVectorStore` 本地文件；
  - 进阶版：Redis Stack / PGVector（Docker 启动）。
- 检索 Top-K，拼进 Prompt，要求回答带引用 `[1]`。
- 建 20 条问答评测集，记录召回率/回答质量。
- 接口：上传、列表、删除、带知识库聊天。

验收：
- 能演示“上传文档 → 提问 → 回答带引用”。
- 能解释 chunk size、overlap、Top-K、embedding 维度。
- 能说出至少两个 RAG 失败案例（切分不好、召回不准、模型编造）。

面试题：
- RAG 的完整链路？
- 怎么评估 RAG 效果？
- 文档很长怎么切？为什么要 overlap？
- 如何防止 Prompt 注入？

### 第 7 周：性能与可观测性

**目标**：能回答“上线后怎么发现问题”。

任务：
- 接入 Micrometer + Prometheus，暴露 `/actuator/prometheus`。
- 记录聊天耗时、MySQL 写入耗时、Redis 命中率、AI 调用失败数。
- 用 k6 或 JMeter 做一次压测（50/100 并发），记录 P95、错误率。
- 用 `EXPLAIN` 检查慢查询，必要时加索引。
- 日志加 traceId（简单版 MDC 即可）。

验收：
- 有一张真实的压测结果图（不是编的）。
- 能解释瓶颈在 AI、数据库还是 Redis。

面试题：
- 接口变慢怎么排查？
- 缓存命中率怎么统计？
- 连接池怎么配？

### 第 8 周：部署与 CI/CD

**目标**：一条命令跑起来，面试可演示。

任务：
- Docker Compose：MySQL、Redis、Ollama、backend、frontend、Nginx。
- Nginx 反向代理，SSE 关闭 buffering、调大超时。
- 健康检查、数据卷、环境变量、`.env.example`。
- GitHub Actions：测试 → 打包 → 构建镜像（可选推 GHCR）。
- README 增加“5 分钟启动”和一键演示步骤。

验收：
- 新机器按 README 能启动。
- 能画部署图，解释每个容器职责。

面试题：
- 为什么需要 Nginx？
- SSE 在 Nginx 下要注意什么？
- 配置和密钥怎么管理？

### 第 9 周：API 文档、前端联调与代码清理

**目标**：项目像一个能交付的作品。

任务：
- 接入 springdoc-openapi，补接口说明和错误码。
- 前端联调分页、停止生成、知识库上传。
- 清理无用代码、统一命名（可选：`impl` 大小写、包名规范）。
- 补架构图、ER 图、核心时序图。
- 统一日志格式和错误提示。

验收：
- Swagger 页面可访问，主要接口可调试。
- 架构图能直接放进简历/面试 PPT。

### 第 10 周：求职材料与模拟面试

**目标**：把项目变成 offer。

任务：
- 写 2 分钟项目介绍和 5 分钟深挖版本。
- 准备 10 个 STAR 故事（缓存、持久化、流式、限流、RAG、压测、故障排查）。
- 简历项目描述 4~6 条，全部可验证。
- 录 3~5 分钟 demo 视频。
- 找同学/自己模拟面试，录音复盘。
- 代码 freeze，只修 bug，不再加功能。

验收：
- 能不看稿讲 5 分钟。
- 每个简历关键词都能展开 2~3 分钟。

## 7. 目标架构

```text
浏览器
  │
  ▼
Nginx（静态资源 + /api 反向代理 + SSE 配置）
  │
  ▼
Spring Boot
  ├── 拦截器链：Token 解析 → 登录校验 → 限流
  ├── ChatService：同步 / SSE / 上下文裁剪
  ├── ChatPersistenceService：MySQL 事务
  ├── RAGService：解析 / 切分 / 检索 / 拼 Prompt
  └── Actuator + Micrometer
  │
  ├── MySQL：用户、会话、消息、知识库元数据
  ├── Redis：Token、验证码、会话缓存、限流
  ├── 向量库：Redis Stack / PGVector
  └── Ollama：聊天模型 + Embedding 模型
```

## 8. 测试策略

| 层级 | 工具 | 测什么 |
|------|------|--------|
| 单元测试 | JUnit 5 + Mockito | Service 分支、异常、边界 |
| Repository 测试 | Mockito | 缓存命中/未命中、回源、失败降级 |
| 集成测试 | Testcontainers + Spring Boot Test | MySQL/Redis 真实读写、事务 |
| API 测试 | MockMvc | 登录、401、参数校验、会话隔离 |
| 压测 | k6 / JMeter | 并发、P95、错误率 |
| 手工验收 | curl / 前端 | 流式、上传、引用 |

原则：
- 不追求 100% 覆盖率，核心链路必须覆盖。
- 每个 bug 修复先补一个回归测试。
- 集成测试不要依赖你本机已经启动的服务。

## 9. 部署方案

最小可用：

```text
docker-compose.yml
├── mysql:8
├── redis:7
├── ollama
├── backend（Spring Boot jar）
├── frontend（Nginx 静态文件）
└── nginx（反向代理 + SSE）
```

注意：
- MySQL/Redis 数据用 volume。
- Ollama 模型用 volume，避免每次重下。
- 后端用环境变量覆盖数据库密码、Ollama 地址。
- Nginx 对 SSE 配置 `proxy_buffering off`、`proxy_read_timeout`。
- 生产环境不要把 MySQL/Redis 端口暴露到公网。

## 10. 简历写法（只写真实做过的）

可选条目：

- 基于 Spring Boot 3 + Spring AI 构建 AI 对话后端，支持同步与 SSE 流式输出、多轮上下文。
- 设计 MySQL + Redis 缓存旁路：消息/会话以 MySQL 为持久化主存储，Redis 提供 7 天热缓存，
  缓存未命中自动回源，解决 Redis TTL 导致历史丢失的问题。
- 使用 `@Transactional` 保证消息与会话元数据一致性，缓存写失败时主动失效并降级到 MySQL。
- 实现 Token 拦截器、验证码一次性/防刷、会话用户隔离、全局异常与参数校验。
- 引入 Mockito + Testcontainers + GitHub Actions，覆盖持久化回源、登录、会话隔离等核心链路。
- 使用 Docker Compose 编排 MySQL/Redis/Ollama/后端/Nginx，完成 SSE 代理与一键启动。
- （如果做了）实现 RAG 知识库：文档解析、切分、Embedding、Top-K 检索与引用回答，
  在自建评测集上达到 xx% 召回率。

不要写：
- “支撑百万用户”“QPS 10 万”这类没有压测依据的数字。
- 自己没讲清楚的技术名词。
- 把教程项目写成“从 0 到 1 自研”。

## 12. 每周节奏

建议每次学习 2 小时：

```text
10 分钟：回顾上周笔记/看板
70 分钟：写代码 + 写测试（不碰 AI）
20 分钟：跑测试、看日志、修问题
10 分钟：记录学习日志 + 提交 Git
```

每周末：
- 30 分钟 demo 自己跑一遍。
- 30 分钟口述本周技术点。
- 更新 README / 看板。

## 13. 4 周压缩版

如果时间不够：

- 第 1 周：持久化测试 + 分页 + 上下文裁剪。
- 第 2 周：限流 + Testcontainers + CI。
- 第 3 周：RAG 最小版（TXT/Markdown + 内存向量库 + 引用）。
- 第 4 周：Docker Compose + 压测 + 简历/模拟面试。

放弃：多模型、管理端、outbox、复杂前端。

## 14. 不要做的事

- 不要为了“微服务”把项目拆成 Spring Cloud。
- 不要为了“高并发”上 Kafka、Kubernetes。
- 不要堆一堆没有测试和文档的 CRUD 接口。
- 不要让 AI 一次生成整个模块，然后自己看不懂。
- 不要写虚假指标。
- 不要过度抽象：这个规模不需要为每个类建接口。
