# 聊天持久化设计

> 对应代码：`ChatPersistenceService` / `ChatPersistenceServiceimpl`、
> `ChatMessageMapper`、`ChatSessionMapper`、`ChatSessionRepositoryimpl`

## 1. 目标

聊天记录原来只存在 Redis，7 天 TTL 到期后不可恢复。本次改造要保证：

1. 会话元数据和消息全量落 MySQL，Redis 过期、重启或宕机后仍能恢复。
2. 正常请求仍然走 Redis，避免每次对话都查库。
3. 不引入消息队列、分布式事务等超出项目规模的组件。

## 2. 存储职责

| 存储 | 角色 | 内容 |
|------|------|------|
| MySQL | 持久化主存储 | `tb_chat_session`、`tb_chat_message` |
| Redis | 7 天热缓存 | 消息 List、会话 ZSet、标题 Hash |

原则：**先写 MySQL，再更新 Redis；读 Redis 未命中时回源 MySQL 并回填。**

这样 Redis 只是加速层，不再承担“唯一数据源”的职责。

## 3. 表结构

### tb_chat_session

- `id`：自增主键，方便以后做管理端/审计。
- `(user_id, session_id)`：唯一键，保证一个用户下会话不重复。
- `title`：会话标题，可为空。
- `create_time` / `update_time`：创建和最近活跃时间。
- `idx_user_update (user_id, update_time)`：支撑会话列表按最近更新时间排序。

### tb_chat_message

- `id`：自增主键，按 id 升序就是稳定写入顺序。
- `(user_id, session_id, id)`：支撑按会话分页查询。
- `role`：`user` / `assistant` / `system`。
- `content`：消息正文。
- `model`：本轮实际使用的模型名；加 `model` 列之前的历史消息为 `NULL`。
- `create_time`：消息时间。

完整建表语句见 `docs/schema.sql`。

## 4. 写路径

### 4.1 保存一条消息

```text
ChatService
  -> ChatSessionRepository.save()
       -> ChatPersistenceService.saveMessage()   [MySQL 事务]
            -> insert tb_chat_message（含 model）
            -> upsert tb_chat_session
       -> Redis rightPush + expire
       -> Redis ZSet add + expire
```

要点：

- 首条消息在写消息前先调用 `saveTitle`，避免 `tb_chat_session.title` 出现 null 中间态。
- MySQL 事务保证“消息 + 会话元数据”同时成功或同时失败。
- Redis 更新失败只记录日志，并删除可能不完整的缓存，下一次读会回源 MySQL。
- 消息落库使用请求时间，而不是异步线程执行时间，避免时间漂移。

### 4.2 保存/修改标题

先 upsert `tb_chat_session`，再更新 Redis Hash，并同步更新 ZSet 分数。
会话列表缓存为空时，从 MySQL 整体重建，避免只写入当前会话导致列表不完整。

### 4.3 清空会话

先在一个事务里删除消息和会话元数据，再删除 Redis 的三个 key。
返回值同时考虑 MySQL 和 Redis：即使 Redis 已过期，只要 MySQL 有数据也算删除成功。

## 5. 读路径

### 5.1 历史消息

```text
读 Redis List
  命中 -> 返回
  未命中 -> 查 tb_chat_message（按 id 升序）
          -> 回填 Redis List（7 天 TTL）
          -> 返回
```

### 5.1.1 历史消息分页（游标）

`/chat/history` 支持 `beforeId`（排他游标）+ `limit`（1~100）：

```text
最新一页：ORDER BY id DESC LIMIT ?
往前翻：  WHERE id < beforeId ORDER BY id DESC LIMIT ?
          -> Java 反转为 id 升序返回
```

设计取舍：

- 用自增 `id` 而不是 `create_time` 做游标，避免同一毫秒内消息边界不稳定。
- SQL 只取一页，命中索引 `(user_id, session_id, id)`，不会随历史增长扫描全表。
- Redis 命中时缓存里是全量历史，直接按 id 过滤后取最近 `limit` 条。
- Redis 未命中时只查 MySQL 的当前页，**不回填 Redis**，避免把“一页”当成全量历史。
- 旧版本缓存没有 `id` 字段时视为未命中，回源 MySQL 后整体重建；历史消息 `model=null` 是合法状态，不作为缓存失效条件。
- 不传 `limit` 时仍返回全量历史，兼容现有前端。

### 5.1.2 长上下文裁剪

历史接口返回全量/分页数据，但送给模型的历史只保留最近 N 条：

- 默认 `app.chat.context-max-messages=20`，`<=0` 表示不裁剪。
- 同步和流式接口共用同一个 `trimHistory()`，避免两条链路行为不一致。
- 裁剪只影响 Prompt，不影响用户查看历史，也不影响 MySQL/Redis 中的数据。

### 5.2 会话列表

```text
读 Redis ZSet（reverseRange）
  非空 -> 返回
  空   -> 查 tb_chat_session（按 update_time 倒序）
        -> 回填 ZSet
        -> 返回
```

### 5.3 会话标题

```text
读 Redis Hash
  命中 -> 返回
  未命中 -> 查 tb_chat_session.title
          -> 回填 Hash
          -> 返回
```

## 6. 一致性说明

这不是强一致方案，而是**以 MySQL 为准的最终一致缓存方案**：

- 写 DB 成功后，Redis 更新失败：数据不丢，下一次缓存未命中会回源。
- 极端情况下 Redis 中可能短暂存在不完整缓存：代码在写失败时主动删除对应 key。
- 多实例部署时，一个实例更新后另一个实例的本地缓存不会立刻失效；本项目通过 7 天 TTL
  和“读时回源”控制影响。真正的多实例强一致需要版本号、发布订阅或 CDC，属于后续优化。

## 7. 为什么不用 @Async 异步落库

之前的实现使用 `@Async` 异步写 MySQL，看起来性能更好，但会带来：

- 消息顺序和“先写用户消息、再写助手回复”的时序难以保证。
- 异步线程失败后不易感知，用户看到成功但数据可能没落库。
- 测试、排查、事务边界都更复杂。

当前阶段选择同步落库：AI 调用本身是百毫秒到数秒级，两条小 SQL 的耗时可以忽略。
如果未来写入量真的成为瓶颈，再引入 outbox + MQ，而不是直接 `@Async`。

## 8. 验证方式

```bash
# 单元测试（不依赖 MySQL/Redis）
./mvnw -Dtest='!AichatApplicationTests' test

# 本地集成验证：启动 MySQL/Redis 后执行建表脚本
mysql -h 127.0.0.1 -P 13306 -uroot -p1234 < docs/schema.sql
```

手工验证步骤：

1. 登录并发一条消息，确认 `tb_chat_message`、`tb_chat_session` 有数据。
2. 删除对应 Redis key，再查 `/chat/history`，应能从 MySQL 恢复。
3. 删除 `/chat/sessions` 对应的 ZSet，再查会话列表，应能恢复。
4. 清空会话，确认 MySQL 和 Redis 都没有残留。
5. 发一条消息后查 `tb_chat_message.model`，确认记录的是本轮实际模型（未传 modelName 时也应是默认模型）。
6. 发超过 20 条消息后查 `/chat/history?sessionid=s001&limit=20`，确认只返回最近 20 条，`beforeId` 可继续往前翻。
7. 查看 AI 请求日志或 Prompt，确认只带最近 20 条历史（默认配置）。

## 9. 面试可讲点

1. 为什么 Redis 只能做缓存，不能做唯一存储？
2. 为什么先写 MySQL 再写 Redis？反过来会怎样？
3. 缓存更新失败怎么处理？为什么不用分布式事务？
4. 为什么消息表用自增 id 排序，而不是只按 create_time？
5. 如果 QPS 升高，如何演进到 outbox + MQ？
6. 多实例部署下，本地缓存/Redis 缓存如何失效？
7. 为什么分页用 `beforeId` 游标而不是 `LIMIT offset`？深分页会有什么问题？
8. 长对话上下文怎么裁剪？裁剪会不会丢关键信息？

## 10. 后续可优化

- 摘要式上下文：当前是滑动窗口，未来可对更早消息做摘要，减少关键信息丢失。
- 归档：冷数据迁移到对象存储/历史表。
- 异步化：outbox 表 + 消息队列，保证最终一致。
- 观测：缓存命中率、MySQL 慢查询、消息落库失败告警。
