# 啃代码路线

> 给"一个月吃透这个项目"用的。**不要从第一个包的第一个类开始读**，按"一次对话真正走过的路径"读，
> 读完一条路径就能自己讲一段，比通读 137 个类有用得多。

先看 `docs/README.md` 的索引和 `docs/路线图.md`，知道**为什么这么设计**；再按下面五条路径读代码。

## 读之前：三种"读法"

| 读法 | 什么时候用 | 产出 |
|---|---|---|
| 顺着请求读（本文件的主线） | 第一次读代码 | 能画出调用链，讲清"一句话发出去发生了什么" |
| 逆着问题读（出了问题再去读） | 已经能跑起来之后 | 定位能力：给一个现象，能找到代码位置 |
| 横向对比读（同一职责有几个实现） | 准备改动/面试前 | 能回答"为什么这里两套存储、两个限流器" |

## 路径 1：一次普通对话（约 40% 的理解成本）

| 顺序 | 文件 | 读的时候盯住 |
|---|---|---|
| 1 | `Controller/ChatController.java` | 入口有几个（`/ask` 与 `/ask-stream`）、参数校验用什么、限流在哪一步 |
| 2 | `Service/impl/ChatServiceImpl.java` | 提示词怎么拼（`PromptBuilder`）、记忆在哪一步注入、流式与非流式的分支 |
| 3 | `Service/impl/ChatPersistenceServiceImpl.java` | MySQL 事务边界在哪、失败回滚了哪些、为什么先落 user 消息 |
| 4 | `Repository/impl/ChatSessionRepositoryImpl.java` | Redis 与 MySQL 谁先写、缓存失效策略 |
| 5 | `Mapper/ChatSessionMapper.java` + `docs/聊天持久化设计.md` | 表结构与分页、裁剪 |

**读完应该能回答**

- 用户消息和 AI 回复分别是哪一刻写进 MySQL 的？中间挂了会留下什么？
- 流式返回时，SSE 怎么保证不串会话（`UserHolder` 为什么在 `preHandle` 里先清）？
- 上下文超长时裁掉的是哪一段？

## 路径 3：意图 → 待确认 → 落库（本项目的差异化，面试重点，约 20%）

| 5 | `utils/IntentPayloadCodec.java` | payload 结构、编解码、为什么校验"确认后必然非空" |

**读完应该能回答**

## 读不懂的时候

1. 先看 `docs/` 里对应的设计文档，还不懂就看 `docs/踩坑记录.md`
2. 用测试当说明书：`src/test/java` 里同名 `*Test` 基本覆盖了边界，测试的 `@DisplayName` 和
   方法名比注释更可信
3. 还看不懂就把问题记下来，攒够三个再一起查——不要在单个类上耗两个小时

## 附录：包职责边界（读代码前先看一眼）

| 包 | 放什么 | 不放什么 |
|---|---|---|
| `Controller` | HTTP 入口、参数校验、登录态读取 | 业务规则、SQL、payload 解析 |
| `Service` | **只放业务接口** | 实现类、DTO、结果对象 |
| `Service.impl` | 接口实现、事务边界、领域编排 | 请求/响应对象、跨领域工具逻辑 |
| `Service.support` | 有 Spring 依赖但不适合做成业务接口的协作组件（`DailyRateLimiter`、`IntentCandidateSanitizer`、`ConfirmationReceiptWriter`） | Controller 直接依赖 |
| `Dto` | 请求/响应、`IntentOutcome`、`IntentExtractionResult`、`ConfirmResult` | 业务逻辑、数据库访问 |
| `Entity` | 数据库行映射 | 对外 JSON 结构 |
| `Mapper` | MySQL 数据访问（注解 SQL） | Redis、业务校验 |
| `Repository` | Redis / 缓存门面 | MySQL SQL |
| `mcp` | MCP 客户端（进程、协议、工具目录） | 业务语义 |
| `utils` | 无状态工具/解析/格式化 | 事务、Mapper 调用 |
| `Config` | 配置绑定、启动校验、路由、拦截器、线程池 | 业务流程 |

**意图链路的类（都是 `*Impl`，构造器注入）**

```text
ChatServiceImpl
  └─ IntentService（接口）→ IntentServiceImpl（只做编排）
       ├─ IntentDetector            粗筛关键词
       ├─ IntentDailyLimiter        日限流（委托 DailyRateLimiter）
       ├─ IntentExtractor（接口）→ IntentExtractorImpl（LLM + 超时）
       │    ├─ IntentPrompts / IntentJsonParser → IntentExtractionResult
       ├─ IntentCandidateSanitizer  候选校验 / 截断 / 敏感词
       ├─ MemoryChangeParser        改/删记忆的规则解析
       ├─ IntentPayloadCodec        pending payload 唯一编解码入口
       ├─ IntentReplyFormatter      文案（不依赖 Spring、不查库）
       └─ PendingActionService      状态机 + 事务
```

几条边界约定（写新代码时守住）：

- `IntentOutcome` 是服务返回结果，放 `Dto`，不可变（`private final` + 工厂方法），调用方只能问 `shouldContinueChat()` 这类问题
- `IntentJsonParser` 只做「JSON → DTO」，不写库、不限流、不生成文案
- `IntentReplyFormatter` 只做文案；需要查数据的一律不放在这里
- `MindButlerStartupValidator` 负责启动期检查，`IntentExtractorImpl` 只负责提取
